## 1. 项目目标

本项目计划开发一个面向 AI Agent 的可信取数平台。平台接入结构化业务数据后，通过业务指标定义、自然语言理解、查询计划生成、数据质量检查和结果追溯，为人类用户或其他 AI Agent 提供可靠的数据查询服务。

项目首版采用零售订单分析场景，围绕订单、退款和客户三类数据完成以下流程：

1. 导入并检查业务数据；
2. 配置字段含义、表关系和指标口径；
3. 接收用户或 Agent 的自然语言问题；
4. 识别指标、时间范围、分组和筛选条件；
5. 对口径不明确的问题进行澄清；
6. 生成并执行安全的只读查询；
7. 返回查询结果、指标口径、数据来源和检查信息；
8. 通过示例运营 Agent 调用平台生成经营简报。

团队协作的基本原则是：

> 成员 1 保证数字正确，成员 2 保证问题理解正确，成员 3 保证产品能用、效果能被证明。

## 3. 成员 1：数据与后端负责人

### 3.1 角色目标

建立稳定、可验证的数据底座，确保系统返回的数值与业务指标定义一致，并向页面和外部 Agent 提供统一的查询服务。

### 3.2 具体职责

#### 3.2.1 设计数据结构

负责确定首版产品使用的数据表、字段类型、主键和表间关系，包括：

- 订单表 `orders`；
- 退款表 `refunds`；
- 客户表 `customers`；
- 订单与退款、订单与客户之间的关联关系；
- 金额、时间、地区和状态字段的含义；
- 数据版本的记录方式。

设计时需要明确以下问题：

- 一个订单是否可能产生多条退款记录；
- 订单编号和退款编号是否唯一；
- 支付时间、下单时间和退款时间如何区分；
- 金额单位是元、分还是万元；
- 取消订单、失败支付和失败退款是否参与统计。

#### 3.2.2 准备项目数据

负责生成或整理三套数据：

1. **小型核对数据**：数据量较小，可以通过人工计算验证指标结果；
2. **正常演示数据**：约 1 万至 10 万条订单，用于产品演示和性能测试；
3. **异常测试数据**：包含重复编号、字段缺失、错误类型和异常金额等问题。

模拟数据需要标记为模拟业务数据，并在项目说明中记录生成方法和限制。

#### 3.2.3 建立指标字典

将业务指标转换成可执行、可复用的计算规则。首版至少支持：

| 指标 | 计算口径 |
|---|---|
| 支付订单数 | 所选期间成功支付的订单数，按订单编号去重 |
| 支付人数 | 所选期间成功支付的客户数，按客户编号去重 |
| 实付金额 | 所选期间成功支付订单的实付金额之和 |
| 成功退款金额 | 所选期间成功完成的退款金额之和 |
| 净销售额 | 所选期间实付金额减去同期成功退款金额 |

成员 1 负责将指标定义写入 JSON、YAML 或其他统一配置，使页面、查询服务和示例 Agent 使用相同口径。

#### 3.2.4 实现数据导入和质量检查

负责实现 CSV 数据导入以及以下检查：

- 必需字段是否存在；
- 字段类型是否符合要求；
- 主键是否重复；
- 必需值是否缺失；
- 金额是否存在负数或异常值；
- 时间字段是否可解析；
- 外键是否能够匹配；
- 数据是否覆盖用户查询的时间范围。

系统发现问题时，需要返回清晰的错误或警告信息，并说明它对查询结果可能产生的影响。

#### 3.2.5 实现查询执行器

接收成员 2 生成的结构化查询计划，将其转换为 SQL 并执行。主要工作包括：

- 支持按时间筛选；
- 支持按地区或客户类型分组；
- 支持排序、排名和时间段比较；
- 正确处理订单和退款的多表关联；
- 防止一对多关联造成订单金额重复累计；
- 限制查询只能读取允许的数据表；
- 设置查询超时和最大返回行数；
- 记录数据版本、查询条件和执行状态。

#### 3.2.6 开发 Agent 查询接口

使用 FastAPI 或等效方案提供查询接口，使网页和其他 AI Agent 调用同一套查询逻辑。接口至少返回：

- 执行状态；
- 查询结果；
- 指标定义及单位；
- 时间范围和筛选条件；
- 来源表及数据版本；
- 数据质量警告；
- 查询记录或 SQL。

### 3.3 主要交付物

- 数据库及三张核心数据表；
- 三套测试和演示数据；
- 数据字典和表关系说明；
- 5 个核心指标的计算逻辑；
- CSV 数据导入模块；
- 数据质量检查模块；
- 安全的查询执行器；
- Agent 查询接口；
- 标准答案计算脚本；
- 接口使用说明。

### 3.4 验收标准

- 固定数据上的指标结果与人工计算一致；
- 多次退款不会导致订单金额重复累加；
- 重复、缺失和格式错误能够被发现；
- 查询服务不能修改原始数据；
- 页面和外部 Agent 对同一问题得到相同结果；
- 接口失败时返回明确状态，不返回伪造结果。

### 3.5 适合人选

优先由团队中 Python、SQL 和数据库基础较好的成员承担。该成员需要做事严谨，能够分析表关系和指标计算错误。

## 4. 成员 2：AI Agent 与智能流程负责人

### 4.1 角色目标

让系统正确理解用户问题，在信息充分时生成可执行的查询计划，在信息不足时进行必要澄清，在数据无法支持结论时明确说明限制。

### 4.2 具体职责

#### 4.2.1 设计 AI 工作流程

负责实现以下完整流程：

```text
接收自然语言问题
        ↓
识别用户意图
        ↓
提取指标、时间、维度和筛选条件
        ↓
判断信息是否充分
        ↓
必要时向用户澄清
        ↓
生成结构化查询计划
        ↓
调用后端查询服务
        ↓
根据结果生成解释
        ↓
返回数据、口径、来源和检查信息
```

#### 4.2.2 设计模型提示词

负责向大模型提供：

- 可使用的业务指标及同义词；
- 可查询的数据表和字段；
- 时间表达的处理规则；
- 哪些情况需要澄清；
- 哪些问题应拒绝回答；
- 查询计划的 JSON 格式；
- 禁止编造数值和因果关系的约束；
- 模型输出不符合结构时的重试或降级策略。

提示词应统一保存和版本管理，避免散落在不同代码文件中。

#### 4.2.3 实现问题解析

从用户问题中提取：

- 指标，如净销售额、实付金额、订单数；
- 时间范围，如 9 月、上个月、第三季度；
- 分组维度，如地区、客户类型；
- 筛选条件，如华东地区、新客户；
- 排序要求，如最高、下降最多、前五名；
- 比较要求，如环比、同比或两个时间段比较。

解析结果需要转换为成员 1 可以执行的结构化查询计划。

#### 4.2.4 实现歧义检测和澄清

负责判断用户问题是否缺少必要信息。例如：

- “销售额是多少”需要确认是实付金额还是净销售额；
- “最近订单怎么样”需要确认时间范围和衡量指标；
- “哪个地区最好”需要确认评价标准；
- “退款多不多”需要确认比较退款金额、订单数还是退款率。

如果业务字典已经设置默认口径，系统可以使用默认规则，但必须在结果中展示所采用的口径。

#### 4.2.5 处理异常和不可回答问题

系统需要区分以下状态：

- 查询成功；
- 需要用户补充信息；
- 当前数据不足；
- 问题超出首版支持范围；
- 查询执行失败；
- 模型输出格式错误。

对于无法由现有数据支持的因果判断，系统应说明缺少的数据，不得根据相关性编造原因。

#### 4.2.6 开发示例运营 Agent

实现一个能够调用平台接口的简单运营分析 Agent。它至少完成以下任务：

1. 接收“生成某月经营简报”的任务；
2. 调用可信取数接口；
3. 获取各地区净销售额及环比结果；
4. 找出下降幅度最大的地区；
5. 形成简短经营分析；
6. 标明数据口径、来源和分析限制。

### 4.3 主要交付物

- AI 工作流代码；
- 模型调用模块；
- 提示词和业务上下文配置；
- 自然语言问题解析模块；
- 歧义检测和澄清机制；
- 查询计划 JSON 结构；
- 异常处理和拒答机制；
- 示例运营分析 Agent；
- AI 模块测试案例。

### 4.4 验收标准

- 同义问法能够映射到相同指标；
- 模糊问题能够提出必要且具体的澄清；
- 明确问题不会被无意义地反复追问；
- 查询计划符合约定的数据结构；
- 数据不足时不会编造答案；
- 示例 Agent 可以调用平台完成完整任务；
- 模型调用失败时，系统能返回可理解的错误状态。

### 4.5 适合人选

优先由对大模型、提示词和 Agent 流程感兴趣，逻辑与语言表达能力较强，并具备基本 Python 能力的成员承担。

## 5. 成员 3：产品前端与测试交付负责人

将数据和 AI 能力整合成评委能够理解、操作和验证的产品，并通过规范测试和演示材料证明产品效果。

## 6. 三人协作接口

### 6.1 整体调用关系

```text
成员 3 开发的产品页面
          ↓ 用户提出问题
成员 2 开发的 AI 智能流程
          ↓ 生成结构化查询计划
成员 1 开发的数据查询服务
          ↓ 返回数据、口径和检查信息
成员 2 组织最终回答
          ↓
成员 3 在页面展示结果和依据
```

### 6.2 查询计划格式

成员 2 向成员 1 提交的查询计划建议采用以下结构：

```json
{
  "metric": "net_sales",
  "date_start": "2026-09-01",
  "date_end": "2026-09-30",
  "group_by": ["region"],
  "filters": {},
  "sort": "desc"
}
```

字段名称一旦确定，需要经过三人同意后才能修改。

### 6.3 查询结果格式

成员 1 向成员 2 和成员 3 返回的查询结果建议采用以下结构：

```json
{
  "status": "success",
  "data": [
    {
      "region": "华东",
      "net_sales": 120000
    }
  ],
  "definition": "成功支付金额减去同期成功退款金额",
  "unit": "元",
  "source_tables": ["orders", "refunds", "customers"],
  "warnings": [],
  "dataset_version": "v1.0"
}
```

### 6.4 接口变更规则

- 接口字段由三人共同确认；
- 任何字段变更都需要同步修改接口文档；
- 变更发起人需要通知另外两名成员；
- 变更后必须完成一次完整联调；
- 10 月 8 日功能冻结后，原则上只修复错误，不修改核心接口。

### 6.5 接口契约补充 v1.1（2026-09-30，成员 3 提出）

§6.3 只定义了 `status = "success"` 的返回结构，其余五种状态（§4.2.5）没有结构定义，
导致页面无法实现澄清分支与异常展示。补充内容见：

- 文档：`docs/接口契约补充_v1.1_澄清与异常结构.md`
- 代码（唯一事实来源）：`shared/contracts.py`

补充要点：

1. 六种状态统一返回的信封字段（`status` / `message` / `query_id` / `dataset_version` / `executed_at`）；
2. `need_clarification` 的 `clarification` 子结构与澄清二次提交协议；
3. `insufficient_data` / `out_of_scope` / `execution_failed` / `model_output_invalid` 的
   `reason` / `missing` / `suggestion` / `retryable` 结构，其中 `missing` 必须具体列出缺什么；
4. HTTP 接口清单：`GET /health`、`POST /agent/query`、`POST /datasets/inspect`；
5. 单次提问最多澄清 2 轮，超过必须降级为「当前数据不足」，不得反复追问；
6. 待确认口径议题 IS-001：净销售额中「同期成功退款金额」的时间归属，
   须在 10 月 8 日功能冻结前由三人确认。

三个模块都必须 import `shared/contracts.py`，禁止在各自代码里另写字面量。

## 9. 每日协作机制

### 9.1 每日短会

每天进行一次不超过 15 分钟的短会。每位成员回答：

1. 昨天完成了什么；
2. 今天将交付什么可运行或可检查的结果；
3. 当前遇到什么问题，需要谁配合。

### 9.2 每日交付要求

每日工作应形成可以检查的产物，例如：

- 一个可调用的接口；
- 一个可运行的页面；
- 一组有结论的测试记录；
- 一份更新后的指标定义；
- 一个已经复现或修复的问题。

不以“正在学习”“正在写代码”作为当天最终交付结果。

### 9.3 代码协作规则

- 所有代码使用 Git 管理；
- 每个功能使用独立分支或清晰的小提交；
- 提交信息说明修改内容；
- 合并前至少由另一名成员检查；
- API 密钥不得提交到仓库；
- 数据、提示词和指标配置需要记录版本；
- 每天结束前将可运行代码提交到共享仓库。

### 9.4 问题处理规则

- 阻塞超过 2 小时，应主动告知团队；
- 接口问题由成员 1 和成员 2 共同定位；
- 页面问题由成员 3 主责，相关接口负责人配合；
- 指标口径争议由三人共同确认并写入指标字典；
- 10 月 8 日后优先修复影响演示和正确率的问题。
