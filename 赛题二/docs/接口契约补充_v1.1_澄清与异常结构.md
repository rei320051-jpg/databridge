# 接口契约补充 v1.1：澄清与异常返回结构

> 项目：数桥 DataBridge —— 面向 AI Agent 的可信取数平台
> 隶属文档：`AI智能体校园黑客松_A赛题_三人分工.md` §6.2 / §6.3 / §4.2.5
> 版本：v1.1　制定日期：2026-09-30　提出人：成员 3
> 唯一事实来源：`shared/contracts.py`（本文件是其可读说明，二者冲突时以代码为准）

---

## 1. 为什么需要这份补充

分工文档 §6.3 只定义了 `status = "success"` 的返回结构。但 §4.2.5 明确规定了**六种**状态，其余五种至今没有定义返回结构。这会造成三个具体阻塞：

1. **页面无法渲染澄清分支** —— §5.2.1 的第 5 步是「回答系统提出的澄清问题」，但澄清响应里应该有什么字段，目前没有任何约定。
2. **澄清后如何二次提交没有约定** —— 用户回答之后，客户端要把什么回传给后端？原问题、已解析出的槽位、选择值如何携带？没有协议就无法实现多轮澄清。
3. **模型输出异常时没有降级路径** —— §4.4 要求「模型调用失败时系统能返回可理解的错误状态」，但错误状态的字段结构未定义。

本文件补齐这三块，并定义 HTTP 接口清单。

## 2. 契约的唯一来源

`shared/contracts.py` 是三方唯一的事实来源。三个模块都必须 `import` 它，禁止在各自代码里另写字面量。

已冻结的枚举（变更需三人同意，并在 2026-10-08 功能冻结后原则上不再改动）：

| 枚举 | 取值 | 说明 |
|---|---|---|
| `Metric` | `paid_order_count` `paid_customer_count` `paid_amount` `refund_amount` `net_sales` | 首版固定 5 个指标，不可自由扩展 |
| `Status` | `success` `need_clarification` `insufficient_data` `out_of_scope` `execution_failed` `model_output_invalid` | 对应 §4.2.5 六种状态 |
| `Dimension` | `region` `customer_type` | 可分组维度 |
| `ReasonCode` | `ambiguous_metric` `ambiguous_criterion` `ambiguous_time_range` `ambiguous_group_by` `ambiguous_filter` `missing_field` | 澄清原因码 |

## 3. 六种状态的通用信封

**无论哪种状态，以下五个字段都必须返回。** 页面依赖它们做状态展示与追溯，缺一即视为接口不合规。

```json
{
  "status": "success",
  "message": "已按「净销售额」口径完成查询。",
  "query_id": "Q20260930112200301",
  "dataset_version": "mock-v1.0-demo",
  "executed_at": "2026-09-30T11:22:00"
}
```

### 3.1 `success` 附加字段

```json
{
  "data": [{"region": "华东", "net_sales": 1156416.0}],
  "columns": ["region", "net_sales"],
  "definition": "所选期间实付金额减去同期成功退款金额",
  "unit": "元",
  "metric": "net_sales",
  "applied_filters": {"region": "华东"},
  "date_start": "2026-09-01",
  "date_end": "2026-09-30",
  "group_by": ["region"],
  "source_tables": ["orders", "refunds"],
  "generated_sql": "WITH paid AS (...) SELECT ...",
  "warnings": [],
  "row_count": 5,
  "truncated": false
}
```

### 3.2 `need_clarification` 附加字段（v1.1 新增）

```json
{
  "clarification": {
    "id": "clr_metric_001",
    "target_field": "metric",
    "reason_code": "ambiguous_metric",
    "question": "你说的「销售额」是指哪一个指标？",
    "options": [
      {"value": "net_sales",   "label": "净销售额", "definition": "实付金额减去同期成功退款金额"},
      {"value": "paid_amount", "label": "实付金额", "definition": "成功支付订单的实付金额之和，不做退款扣减"}
    ],
    "allow_free_text": true,
    "resolved_context": {"clarification_round": 0},
    "round": 1
  }
}
```

**字段约束：**

- `id` 必须遵循 `clr_<target_field>_<三位序号>` 规则，例如 `clr_metric_001`。
  客户端只需回传 `id` 与 `choice`，服务端即可无状态恢复上下文，不依赖服务端会话。
- `options` 建议 2~5 项。为空表示只能自由文本回答。
- `allow_free_text` 为 `true` 时，页面需要同时提供文字输入入口。
- `round` 记录第几轮澄清。达到 `MAX_CLARIFICATION_ROUNDS = 2` 后**必须**降级为 `insufficient_data`，不得继续追问 —— 对应 §4.4「明确问题不会被无意义地反复追问」。

### 3.3 其余四种状态附加字段（v1.1 新增）

`insufficient_data` / `out_of_scope` / `execution_failed` / `model_output_invalid` 统一附加：

```json
{
  "reason": "causal_reasoning_unsupported",
  "missing": ["营销活动数据", "竞品数据", "价格调整记录"],
  "suggestion": "现有数据只能反映结果指标的变化，无法判断下降原因。可以改为查询「华东地区各月净销售额」观察变化幅度。",
  "retryable": false
}
```

- `missing` 必须**具体列出缺什么**，而不是笼统写「数据不足」。这是「可信」的核心体现。
- `retryable = false` 时，页面不应提供重试按钮。
- `out_of_scope` 的 `suggestion` 应引导用户到首版支持的范围内，或说明如何自行计算。

## 4. 澄清二次提交协议

澄清只有一个入口，不需要单独的 `/agent/clarify` 接口 —— 减少一处接口即减少一处不一致的可能。

```
POST /agent/query
```

```json
{
  "question": "9月的销售额是多少",
  "context": {"clarification_round": 0},
  "clarification": {
    "id": "clr_metric_001",
    "target_field": "metric",
    "choice": "net_sales",
    "free_text": null
  }
}
```

**规则：**

1. `question` 必须传**原始问题**，不能传澄清后的改写版本。
2. `context` 必须原样回传上一轮返回的 `resolved_context`（含 `clarification_round`）。
3. `choice` 优先；`free_text` 非空时以 `free_text` 为准，服务端需做同义词归一化（见 `contracts._normalize_choice` 的等价逻辑）。
4. 服务端不得依赖任何会话状态。只靠 `id` + `context` 重新解析即可。

## 5. `/datasets/inspect` 返回结构（v1.1 新增）

```json
{
  "status": "ok",
  "dataset_version": "v1.0",
  "tables": [
    {
      "name": "orders",
      "rows": 85018,
      "columns": 6,
      "primary_key": "order_id",
      "field_types": {"order_id": "文本", "pay_amount": "数值", "pay_time": "时间"},
      "issues": [],
      "error_count": 0,
      "warning_count": 2
    }
  ],
  "cross_table_issues": [
    {
      "level": "error",
      "code": "orphan_foreign_key",
      "field": "orders.customer_id -> customers.customer_id",
      "count": 1,
      "message": "`orders.customer_id` 有 1 条无法在 `customers.customer_id` 中找到对应记录。",
      "impact": "关联后这些记录的分组维度会变成空值，按地区统计时总额对不上。"
    }
  ],
  "issues": [],
  "total_errors": 0,
  "total_warnings": 2,
  "inspected_at": "2026-09-30T11:22:00"
}
```

每一条 issue 必须包含 `impact` 字段，说明**这个问题会怎样影响查询结果**。只报「有重复值」而不说后果，对取数平台没有价值。

## 6. HTTP 接口清单

| 编号 | 方法 | 路径 | 主责 | 说明 |
|---|---|---|---|---|
| 1 | GET | `/health` | 成员 1 | 返回 `{"status":"ok","dataset_version":...,"tables":[...]}` |
| 2 | POST | `/agent/query` | 成员 2（入口）+ 成员 1（执行） | 自然语言取数，含澄清二次提交 |

## 7. 待三人确认的口径议题

### IS-001：净销售额中「同期成功退款金额」的时间归属

分工文档 §3.2.3 只写了「净销售额 = 所选期间实付金额 − 同期成功退款金额」，未说明退款按哪个时间字段归属期间。不同理解会得出不同的数字。

- **方案 A（两条独立聚合）**：实付金额按 `pay_time` 归属期间，退款金额按 `refund_time` 归属期间，两者分别求和后相减。
- **方案 B（按订单归属）**：退款金额归属于「原订单支付时间」所在的期间。

页面侧参考实现 `app/mock_backend.py` 采用**方案 A**，理由：

1. 与 §3.2.3 对「成功退款金额」的定义完全一致（按退款发生时间）；
2. 两条聚合彼此独立，结构上不可能发生一对多重复累计，从根上满足 §3.4「多次退款不会导致订单金额重复累加」的验收标准。

**无论选哪种，当查询需要按地区或客户类型分组时，退款侧都必须先按 `order_id` 预聚合，再经 `orders → customers` 取维度。禁止 `orders ⨝ refunds` 明细连接后再 `SUM(orders.pay_amount)`。**

> 结论须在 2026-10-08 功能冻结前由三人确认。确认后更新 `contracts.NET_SALES_TIME_ATTRIBUTION` 并递增 `MODULE_VERSION`。
