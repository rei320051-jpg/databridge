数桥 DataBridge · 可信取数平台

面向 AI Agent 的可信取数平台。每一个数字都附带指标口径、来源表、数据集版本与可追溯的查询记录； 当数据无法支持结论时，明确说明缺什么，而不是编一个答案。
只读 · 不修改任何业务数据 5 个固定指标口径 口径不明确时先澄清 最多澄清 2 轮 零售订单分析场景
本页为静态展示页，用于答辩与演示；可运行的真实产品为 app/app.py（Streamlit）。 页面内所有数字均由平台真实计算得出，取自 tests/export_showcase_data.py 的导出结果。

01与普通 Text-to-SQL 的区别

同样是「问一句话拿到数字」，差别在于：这个数字能不能被信任、能不能被追溯。

普通方案：大模型根据表结构直接生成 SQL
  • 指标口径由模型临场理解，同一问题换个说法可能得到不同结果
  • 遇到「销售额」这类歧义词，直接猜一个口径就返回
  • 通常不返回来源与版本，无法回答「这个数从哪来」
  • 看不到执行的 SQL，错了也不知道错在哪
  • 数据有重复、缺失、负金额时照算不误
  • 数据不支持时，容易编一个听起来合理的原因
数桥：业务字典 + 查询计划 + 澄清 + 结果检查
  • 5 个指标写进业务字典，页面、查询服务、Agent 共用同一份定义
  • 命中歧义词表必须先澄清，并列出候选口径供选择
  • 每次查询都返回来源表 + 数据集版本
  • 返回可追溯的查询记录 SQL，只读三张表，不含写操作
  • 每条数据质量问题都带「对查询结果的影响」说明
  • 数据不足时列出缺什么，并给出可替代的问法

03净销售额不是估算，而是可校验的等式

实付金额7,786,231.39

净销售额6,830,343.55
支付订单数766
支付人数627
为什么不会出现「重复累计」

一个订单可能对应多条退款。如果直接把 orders 与 refunds 做明细连接再求和，实付金额会被按退款条数放大。

数桥的做法是：实付金额与退款金额两侧各自独立聚合，结构上不可能重复累计； 正式库的地区是订单快照（orders.region），退款侧先按 order_id 预聚合，再连接 orders 取地区。

导入器硬性校验「同一订单累计成功退款 ≤ 实付金额」，违反即拒绝入库： demo-v1.1 全库 20,000 单超额退款 0 例； 另经不变量验证：追加 5 条各 1000 元退款，净销售额精确下降 5000 元，实付金额完全不变。

04口径不明确时，先问清楚，不猜

查询记录（SQL，可追溯）
-- 成员 1 正式执行层真实 SQL（金额为整数分，半开时间区间，地区取订单快照）
-- ① 实付侧：只计 payment_status='paid'，直接按 orders.region 聚合
SELECT o.region AS region,
       COALESCE(SUM(o.paid_amount_fen), 0) AS value
FROM orders o
WHERE o.payment_status = 'paid'
  AND o.paid_at >= '2026-09-01T00:00:00'
  AND o.paid_at <  '2026-10-01T00:00:00'
GROUP BY o.region;

-- ② 退款侧：只计 refund_status='success'，按退款完成时间；
--    先按 order_id 预聚合（防一对多扇出），再连接 orders 取地区
SELECT o.region AS region,
       COALESCE(SUM(r.refund_amount_fen), 0) AS value
FROM refunds r JOIN orders o ON o.order_id = r.order_id
WHERE r.refund_status = 'success'
  AND r.refunded_at >= '2026-09-01T00:00:00'
  AND r.refunded_at <  '2026-10-01T00:00:00'
GROUP BY o.region;
-- 净销售额 = (① - ②) / display_divisor(100)，只读，不含任何写操作
平台只读取 orders / refunds / customers 三张表，生成的 SQL 不含任何写操作。最多澄清 2 轮，超过即降级为「当前数据不足」，不会反复追问。

05数据不支持时，说明缺什么，不编原因

问「为什么下降」是最容易让模型编造的场景。数桥的回答是明确拒绝，并列出缺什么。

用户为什么华东地区9月净销售额下降了
数桥 · 当前数据不足（causal_reasoning_unsupported） 现有数据只能反映结果指标的变化，缺少活动、价格、竞品等外部变量，无法判断下降原因。 可以改为查询「华东地区各月净销售额」观察变化幅度。
系统明确列出缺少的信息
  • 营销活动数据
  • 竞品数据
  • 价格调整记录
  • 库存与履约数据
接口字段：status=insufficient_data、reason、 missing、suggestion、retryable=false。 missing 必须具体列出缺什么，而不是笼统写「数据不足」。

06取数之前，先告诉这份数据能不能用

每一条数据质量问题都附带「对查询结果的影响」——只报「有重复值」而不说后果，对取数平台没有价值。

08当前限制（如实说明）

  • 演示数据为模拟业务数据，由 scripts/generate_datasets.py 固定种子生成（demo-v1.1），覆盖 2026-01-01 ~ 2026-09-30，订单 20,000 条。任何结论都不代表真实经营情况。
  • 本页数字来自成员 1 正式执行层（FastAPI + SQLite，整数分入库）与成员 2 Agent 工作流（/agent/query）；页面 live 模式与之直连，mock 模式为现场保底。
  • 首版支持 5 个基础指标 + 3 个派生指标（退款率、客单价、支付人均消费，v1.2 冻结）：比率一律"先汇总分子分母再相除"，分母为零返回 null；复购率、转化率等仍明确拒答。
  • 口径议题 IS-001 已于 2026-10-04 三人确认（方案 A：退款按退款完成时间归属）；正式库实测跨月退款占比 44.28%（金额占比 45.55%），该口径使历史月份零漂移。
  • 订单表内含 paid / cancelled / failed 订单，退款表内含 success / failed / pending 退款；非成功行不参与任何指标统计。地区为订单下单时快照，同一客户跨地区下单时不做客户维度归并。
  • S1 对照基线目前是确定性行为模拟（无真实 LLM 调用）；成员 2 真实大模型接入后需用同一模型重测对照实验。
