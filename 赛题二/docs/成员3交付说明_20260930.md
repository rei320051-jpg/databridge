## 3. 关键设计决策

**决策 1：模拟后端不是硬编码数字，而是真正用 pandas 计算。**
`app/mock_backend.py` 先生成 orders / refunds / customers 三张真实结构的表（85,018 条订单），再由表计算指标。因此页面展示的每个数字都是真实查询结果，可以直接用来交叉验证成员 1 的接口实现是否一致。

**决策 2：用 mock/live 双模式解耦依赖。**
接口未就绪时用 `mock` 跑通全流程；成员 1 的服务上线后把模式切到 `live`，**页面代码零改动**。这避免了「等接口 → 页面无法开工」的阻塞。

**决策 3：契约写进代码，而不是只写在文档里。**
`shared/contracts.py` 是三方唯一事实来源。指标、状态、维度、澄清原因码全部以常量形式存在，成员 1 / 2 / 3 都 import 它，从机制上杜绝「文档说一套、代码写一套」。

**决策 4：演示数据故意混入干扰行。**
订单表内包含 failed / pending / cancelled 状态的订单，退款表内包含 failed 退款。这些行不得参与统计 —— 直接对应分工文档 §3.2.1「取消订单、失败支付和失败退款是否参与统计」这一待明确问题，并可用于验证成员 1 的实现是否正确过滤。

## 4. 自测结果

### 4.1 链路自测（24 项，全部通过）

```
[1] 状态覆盖：10 条预设用例全部命中预期状态
    覆盖 success / need_clarification / insufficient_data / out_of_scope
[2] 澄清闭环：指标口径歧义 → 选择 → 成功返回        PASS
[3] 澄清闭环：评价标准歧义（「哪个地区最好」）        PASS
[4] 防无限追问：连续两轮后降级为 insufficient_data   PASS
[5] 分地区之和 == 汇总值（分组不丢行、不重复）        PASS
    净销售额 == 实付金额 - 成功退款金额（逐地区）      PASS
[6] 追加 5 条同订单退款后，净销售额精确下降 5000       PASS
    追加退款不影响实付金额（无重复累计）              PASS
[7] 干扰行存在且被排除                               PASS
[8] 异常数据集五类注入问题全部被检出                   PASS
    干净数据集 0 个严重问题                           PASS
[9] 连接失败 / 返回非 JSON 时抛出明确异常，不伪造结果   PASS
```

其中 **[6] 是分工文档 §3.4 的核心验收项**：给同一个订单追加 5 条各 1000 元的退款，净销售额必须精确下降 5000 元，而实付金额必须**完全不变**。这条直接证明一对多关联没有造成订单金额重复累计。

生成性能：演示数据生成耗时由 63.6 秒优化至 **0.20 秒**（改为向量化构造）。
