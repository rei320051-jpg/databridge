## 三、技术社区长文（掘金 / 知乎二选一，D3 发、D5 可发成果更新版）

**标题：** 我们把 Text-to-SQL 放进零售业务里考了 37 道题：0 分，然后修到了满分

**正文：**

> 数联科技 × 华东师范大学 AI 智能体校园黑客松参赛记录。我们做了一个面向 AI Agent 的可信取数平台「数桥 DataBridge」。这篇文章讲清楚一件事：Text-to-SQL 早就不是难点，难的是**出来的数字能不能信**。

## 一、同一个问题，两个数字，差 96.8 万

我们用固定种子生成了一份 2 万订单的零售数据集（2026 年 1–9 月，5 个地区），问系统同一个问题：**2026 年 9 月的净销售额是多少？**

- 普通 Text-to-SQL 方案：**18,166,729.12 元**
- 数桥（带治理层）：**17,198,835.91 元**（数据集参考真值）
- 差额：**967,893.21 元，+5.63%**

最危险的是：前者的 SQL 完全可以执行，没有任何报错。这种数字写进汇报，就是一场事故。

## 二、37 道业务题，裸考 0 分

我们准备了 37 道开发题，覆盖查数、歧义、派生比率、越界请求。直接让 Text-to-SQL 裸考：

| 指标 | 结果 |
| --- | --- |
| 任务完成 | 0 / 37 |
| 数值错误（元数据对、数字错） | 21 |
| 无依据编造（因果 / 预测 / 写操作） | 8 |
| 正确澄清 | 0 |

致错原因彼此独立，我们用"每次只引入一个缺陷"的方法归因：

1. **18 题：未排除失败订单。** failed / pending / cancelled 订单和失败退款混进统计。
2. **16 题：JOIN 一对多扇出。** 订单表 JOIN 退款明细，一单多退时实付金额被按退款条数重复累计。
3. **13 题：退款按支付月归属。** 后续退款会持续回溯改写已结账的历史月份——我们的正式数据里 44.28% 的退款是跨月的，跨月退款金额占 45.55%。

## 三、四层治理：让数字回到真值

1. **统一业务字典**：5 个基础指标 + 3 个派生比率（退款率、客单价、支付人均消费）写进三方共享的契约文件，页面、Agent、SQL 服务 import 同一份定义，禁止字面量。派生比率遵循"先汇总分子分母再相除"，分母为零返回 null 而不是 0。
2. **两轮澄清**：命中歧义词必须先问。"销售额"在净销和实付之间当月相差 2,215,080.08 元，这个选择权必须还给用户；模糊评价（"哪个地区最好"）同样追问。
3. **安全聚合**：支付与退款两侧独立聚合，退款先按订单预聚合再关联订单快照，结构上消除一对多重复。验证方式很朴素：同一订单追加 5 笔各 1000 元退款，净销必须精确下降 5000，实付不动。退款口径经三人评审冻结为"按退款完成月归属"（IS-001 方案 A），历史月份零漂移。
4. **边界护栏**：因果归因、预测、写操作、未定义指标各自有明确原因码，拒答时告诉用户缺什么、可以怎么问。

## 四、真实大模型复测：67 个数字一个没变

治理层本身是确定性的。但接了真实大模型还守得住吗？我们接入了 DeepSeek（OpenAI 兼容接口），架构上让模型**只做"问题 → 结构化槽位"**，之后的字典校验、澄清、SQL 生成、聚合、拒答全部在本地完成，模型全程接触不到数据库。

2026-10-06 用真实 API 全量复测：

- 开发集 37 题：**37/37 正确**
- 保留集 30 题（开发全程没看过的盲测题）：**30/30 正确**
- 模型与离线规则的响应信封（含全部数据行）：**67/67 逐字段一致**
- 无依据编造 0，终态失败 0（1 题瞬时异常，重试后一致）
- 67 题中 54 题真实调用模型、**13 题在调用前就被护栏拦截**（问题不外发，零 token）
- 平均时延 0.93 秒 / 题（p90 1.03 秒）；实付成本约 **0.023 元**人民币（缓存命中 62,208 token）

我们的结论是：**模型负责语言理解，信任由本地治理保证。** 换模型供应商不需要改一行业务逻辑——这正是把"会聊天的模型"和"企业敢用的数字"隔开的那一层。
