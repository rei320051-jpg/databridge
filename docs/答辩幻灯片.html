01 · 问题

AI 取数的门槛，已经不是"写不写得出 SQL"

① 各说各话

"9月销售额"是净销 1,720 万还是实付 1,941 万？两个口径相差 221.5 万元，没人说得清该用哪个。

② 错而不自知

SQL 能跑、不报错，但把取消订单算进来、退款被一对多重累计——9 月净销虚高 96.8 万元。

③ 自信地编造

问"为什么华南跌了""预测下个月"，模型给一段听起来合理的话，但数据根本不支持，还可能执行写操作。

Text-to-SQL 解决了"能不能拿到数"，没解决"这个数字能不能信"。demo-v1.1 · 2026-09
企业里真正出事的是这三种：口径没对齐、数字错了看不出来、AI 越界或编造。

04 · 防线一 · 业务字典

8 个指标，只有一种算法

基础指标（5）口径要点
支付订单数 / 支付人数成功支付，按 ID 去重
实付金额不做退款扣减
成功退款金额按退款完成时间
净销售额实付 − 同期成功退款
派生比率（3，v1.2）公式
退款率退款 ÷ 实付
客单价实付 ÷ 订单数
支付人均消费实付 ÷ 支付人数

为什么退款率分母用实付，不用净销？

若用净销售额做分母：退款越多 → 分母越小 → 退款率被反向放大，出现"退款越严重、率越虚高"的悖论。

比率铁律：先汇总分子分母、再相除；分组比率不能算术平均回整体；分母为零返回 null 而不是 0。

页面 / Agent / 执行层 import 同一份契约，三方不可能出现两套口径。DM-002
Agent 不临场理解指标。退款率分母写死是实付金额，避免退款越多率越被放大的悖论。

08 · 防线四 · 边界

不支持就说不支持，绝不编

用户问题数桥回答机器原因码
为什么华南 9 月净销售额下降？数据不足：缺营销/竞品/价格/库存数据，可改查各月变化causal_reasoning_unsupported
预测一下下个月净销售额只查询历史已发生数据，不做预测建模no_forecast_capability
把订单表里 9 月的记录删掉只读平台，拒绝任何写操作write_operation_refused
复购率是多少？二期指标，当前拒答（退款率/客单价/人均已支持）derived_metric_unsupported

每条拒答都带 reason missing suggestion retryable——拒答不是能力缺失，是可信承诺。

10 · 结果依据

每个数字，都能翻出它的底账

用户提问
  → 共享契约（指标/枚举/白名单）
  → 结构化查询计划 JSON
  → 只读参数化 SQL（半开区间，禁写）
  → 结果 + 质量警告 + query_id

GET /v1/query-records/{query_id}
  → 当时执行的 SQL 模板与参数，可复查

注入与越权实测

' OR 1=1 -- 类输入 → 422 拒绝；DELETE/UPDATE 在计划校验与数据库只读连接两层被挡。

只读不变量

测试前后数据库文件 sha256 不变；查询记录写入独立目录，业务库零修改。

数字之外，还返回它的整个生产过程：口径、来源表、SQL、数据集版本。成员 1
现场可以在结果依据页直接看到真实 SQL 和 query_id，任何一个数字都能复查它怎么来的。

14 · 当前限制（如实说明）

边界讲清楚，数字才可信

  • 数据为固定种子生成的模拟业务数据（2 万单，2026-01~09），任何结论都不代表真实经营。
  • S1 为确定性行为基线；真实大模型的准确率/成本/时延尚未测量——模型适配器已就绪，待密钥接入用同一模型重测。
  • 派生比率在 Agent 层组合两次分量查询实现；结构化 /v1/query 仍只接受 5 个基础指标。
  • 首版 2 个维度（地区 / 客户类型）、5 基础 + 3 派生指标；同比、预测、因果归因、复购率不做。
  • 尚未在另一台电脑做全新部署验证；页面上传/激活闭环未纳入本次演示范围。
分工文档 §10：如实说明模拟数据、测试条件与产品限制。不使用未验证数据
主动讲限制是加分项。我们没有在报告里使用任何没跑过的准确率。
