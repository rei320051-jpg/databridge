## 0. 使用前必读（三条铁律）

1. **时长以官方规则为准**：本脚本按 **10 分钟主讲 + 5 分钟问答** 编排，并给出 **5 分钟精简版**
   （见 §4）。开赛前必须从赛事通知确认实际时长，据此删减，不得超时。
2. **数字只能念本文件 §5 表里的**：每个数字都标注了出处文件，台上不得口算或凭记忆报数。
3. **诚实声明不可省**（分工文档 §10）：演示中必须主动说明——数据为模拟数据；
   S1 对照实验当前是确定性行为基线、不是大模型实测；后端与示例 Agent 目前为页面侧参考实现，
   成员 1 / 成员 2 的正式接口接入后数字需重跑验证。

## 1. 一句话故事（全场主线）

> **大模型直接对着数据库写 SQL，会"自信地给出错误数字"甚至执行危险操作；
> 数桥在人和数据库之间加了一层"可信取数"——统一口径、歧义先问、超界拒答、结果可追溯，
> 让每一个数字都解释得清、追得回源头。**

开场和收尾都回到这句话，中间所有操作都是它的证据。

## 3. 十分钟主讲分镜

> 「操作」列与页面按钮逐字对应，照做即可；「台词」只写要点，不要照读。

### 3.1 开场痛点（0:00–1:30）

- **屏幕**：`产品展示页.html` 封面（浏览器提前打开）。
- **台词要点**：
  - AI 取数听起来简单：把问题交给大模型，让它生成 SQL。
  - 但企业里真正出事的是三种情况：**数字错了还看不出来、口径没对齐各说各话、AI 越界或编造**。
  - 数桥只回答一件事：**怎么让 Agent 给出的每个数字都可信。**
- **转场**：切到 Streamlit 页面（`http://localhost:8501`，演示前已启动）。

### 3.2 数据接入与质量检查（1:30–2:45）

- **操作**：停在「① 数据接入」页，页面已自动加载内置演示数据并完成质检。
- **台词要点 + 可念数字**：
  - 8.5 万条订单、15,139 条退款、59,490 个客户，上传即自动质检，无需点按钮。
  - 干净数据：**0 个严重问题、0 条警告**，每条问题都会标明"对查询结果的影响"。
  - 版本号由**数据内容哈希**生成（不是时间戳），同一份数据重复上传版本不变——这是结果可追溯的锚点。
- **加演（时间够才做，约 20 秒）**：勾选「载入异常测试数据集」→ 出现 **6 个严重问题、5 条警告**
  （重复主键、负金额、脏时间、悬空外键……）→ 红色提示"这些问题修复前，查询结果不能作为结论"。
  → 再取消勾选回到干净数据。

### 3.3 业务字典：口径先对齐（2:45–3:30）

- **操作**：切到「② 业务字典」，快速滚动指标表 → 歧义词表 → 表关系图。
- **台词要点**：
  - 5 个指标的定义、公式、同义词写在一份冻结契约里，页面、后端、Agent 三方同源。
  - 重点指两处：
    - **歧义词表**："销售额/营业额"到底算不算退款？系统不猜，必须问。
    - **一对多风险提示**：一个订单可有多笔退款，直接 JOIN 会把实付金额重复累加——
      正确做法是退款先按订单预聚合。

### 3.4 智能取数：四个对比瞬间（3:30–7:00，全场高潮）

**瞬间 A｜正常取数（约 40 秒）**
- 操作：「③ 智能取数」→ 点快捷示例 **「2026年9月各地区的净…」**。
- 讲解：毛玻璃 KPI 卡给出 9 月净销售额 **4,119,702 元**；柱状图一眼看出华东最低；
  环比列显示**华东 −13.67%**，而华南 +2.62%、西南 +4.78%——有涨有跌，故事可信。

**瞬间 B｜歧义必须澄清（约 50 秒）**
- 操作：点 **「9月的销售额是多少」** → 出现澄清卡片，注意提示"**第 1/2 轮**"。
- 讲解：系统没有偷偷选一个口径，而是让用户在「净销售额 / 实付金额」之间选，并给出两个定义。
- 操作：选「净销售额」→ 提交 → 返回 **4,119,702 元**，与 A 完全一致。
- 一句话钉住："同一批人、同一个词，从此不会再吵出两个数字。"

**瞬间 C｜不知道就说不知道（约 45 秒）**
- 操作：点 **「为什么华东地区9月净销售额下降了」**。
- 讲解：系统返回**数据不足**，并**具体列出缺什么**——营销活动、竞品、价格调整、库存履约数据，
  还给出可执行的替代问法。它拒绝编造因果。
- 可补一句：连续澄清最多 2 轮，超过也降级为"数据不足"，绝不靠猜硬答。

**瞬间 D｜越界坚决拒绝（约 45 秒）**
- 操作：点 **「把订单表里9月的记录删掉」**。
- 讲解：平台是只读的，任何删除/更新请求直接拒绝，SQL 里也不可能出现写操作。
- 时间够可再点「预测一下下个月的净销售额」「华东地区的退款率是多少」，
  分别说明：不做预测、首版不支持派生比率（引导用户分开查分子分母）。

### 3.5 结果依据：每个数字都能翻底账（7:00–8:00）

- **操作**：切到「④ 结果依据」。
- **台词要点**：
  - 一次成功查询完整展示：指标定义、来源表、时间与筛选、**数据集版本号**、质量警告、SQL。
  - 指着 SQL 里的 `refund_pre` 说：退款先按 `order_id` 预聚合，再与支付侧外连接——
    这正是 §3.3 那条风险在工程上的落地。
  - 收尾切「⑤ Agent 调用回放」：其他 Agent 走同一个接口、拿同一套口径，页面和外部 Agent 不会给出两个答案。

### 3.6 实验证据：不是自夸，是跑分（8:00–9:15）

- **屏幕**：`产品展示页.html` 的对照实验区块，或 PPT 同内容图表。
- **台词要点**（开发集 37 题，逐题真实计算）：

  | | S1 直接 Text-to-SQL | S2 数桥完整方案 |
  |---|---|---|
  | 正确回答 | **0 / 37** | **37 / 37** |
  | 无依据编造/越权 | **10 次** | **0 次** |
  | 正确澄清 | 0 | 7 |

  - 最扎心的一点：S1 的 20 道可答题**全部返回了看起来正常的数字**，SQL 能跑、不报错，
    但数字是错的——9 月净销售额它报 449.6 万，比真实值 412 万虚高约 9.1%。
  - 保留集 30 题同样 30/30、编造 0，且保留集**从未用于调参**，是真实泛化能力。
  - **诚实声明（必说）**：S1 目前是确定性的行为基线，成员 2 的大模型接入后会用真实模型重跑；
    今天展示的是治理层带来的增量。

### 3.7 边界、路线图与收尾（9:15–10:00）

- **主动讲限制**（反而加分）：模拟数据；首版仅 5 个基础指标；正式后端/Agent 由成员 1、2 接入；
  IS-001 退款时间归属已有对比实验支撑、按 refund_time 归属的建议待三人 10-08 冻结。
- **下一步**：真实大模型重跑 S1/S2 → 接正式 FastAPI 与 Agent → 扩指标与数据源。
- **收尾回扣主线**："AI 取数的门槛从来不是能不能写出 SQL，而是数字能不能被信任。数桥做的就是这层信任。"

## 6. 评委提问预案（分工文档 §11 七个公共问题）

1. **解决了什么问题**：AI 取数的可信度——错数、口径分歧、编造与越权，不是"能不能查"。
2. **与普通 Text-to-SQL 的区别**：业务字典、查询计划、歧义澄清、只读护栏、结果可追溯；
   有 37 题对照实验为证（0/37 vs 37/37）。
3. **为什么选零售场景**：三表关系典型（含一对多退款）、金额口径冲突高频、指标少而完整，适合首版立标杆。
4. **数据从哪里来**：模拟数据，生成逻辑在 `demo_data.py`，月度/地区总量受控、环比故事可复现；正式数据由成员 1 接入。
5. **如何证明结果正确**：测试集双层判定（状态+元数据+数值）、保留集隔离、smoke/F 场景/live 三套自动化、
   内容哈希版本追溯；核心验收"追加 5 笔千元退款，净销售额精确降 5000、实付不变"。
6. **当前限制**：模拟数据；5 个基础指标；后端与 Agent 为参考实现；S1 尚非真实大模型实测；IS-001 待冻结。
7. **下一步**：真实 LLM 重跑对照实验 → 成员 1 FastAPI / 成员 2 Agent 联调 → 派生指标、更多数据源与场景。

**可能的尖锐提问**：
- "37 题全对是不是过拟合？" → 保留集 30 题全程隔离只读，修复只回写开发集，泛化提升有方法论记录。
- "S1 为什么 0 分？是不是故意做弱？" → S1 复刻的是直接 Text-to-SQL 的六类已知失败模式，
  且全部在同一数据上真实计算；这正是对照实验的目的，接入真实大模型后会重跑并公开结果。
- "净销售额为什么这么算？" → 退款先按订单预聚合防扇出；时间归属有 IS-001 跨月退款实验，推荐按 refund_time。
